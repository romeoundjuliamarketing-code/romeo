# i18n: Deutsch + Englisch – Design

Stand: 2026-10-06

## Ziel
Die App ist vollständig auf Deutsch und Englisch nutzbar. Ein Nutzer mit Sprache Englisch sieht
keinen deutschen Text mehr: Screens, Fehlermeldungen, Datumsangaben, Challenge-Karten, Regeln,
Push-Benachrichtigungen, Benachrichtigungsliste, Rechtstexte.

## Entscheidungen
- Sprache in den Einstellungen wählbar (Deutsch / English).
- Erster Start: Gerätesprache (`de*` → Deutsch, sonst Englisch). Danach gilt die Wahl.
- Wahl wird lokal (AsyncStorage) und in `profiles.language` gespeichert (geräteübergreifend,
  Server braucht sie für Push-Texte).
- Umschalten wirkt sofort, ohne Neustart.
- Nutzerinhalte (Chats, Bios, Gym-/Venue-Beschreibungen, Eventtitel) werden nicht übersetzt.
- Website sparrapp.com nicht im Scope.
- Bibliothek: `i18next` + `react-i18next` + `expo-localization`.

## Teilprojekte
1. **Grundgerüst** (dieses Dokument, Detail unten).
2. **App-UI:** alle hartcodierten Texte (~145 Dateien) bereichsweise auf `t()` umstellen
   (Auth/Onboarding, Map/Sparring, Profil, Chats, Gym/Venue, Paywall/Settings), inkl. lokaler
   Push in `useProximitySparringNotifications` und Umstellung aller `toLocale*String('de-DE')`
   auf `formatDate`.
3. **Inhaltsdaten:** `src/data/` (Challenge-Karten, Regeln, Disziplinen, Kartenrahmen …) mit
   DE/EN-Feldern; neue Challenge-Karten direkt zweisprachig.
4. **Server/Push:** Notifications-Liste übersetzt clientseitig aus `type` + `data`; Push-Text
   wählt der Server anhand `profiles.language` (NULL = Deutsch). Alte App-Versionen bleiben kompatibel.
5. **Rechtliches/Store:** Impressum, Datenschutz, Paywall-Pflichttexte, App-Store-Metadaten EN.

Parallele Arbeit: Teil 1 berührt wenige Dateien. Während Teil 2 läuft, keine parallelen
UI-Text-Änderungen an nicht umgestellten Screens; neue Texte ab Teil 1 immer über `t()`.

## Teil 1 – Grundgerüst

### Struktur `src/i18n/`
- `locales/de.ts` – deutsche Texte als `as const`-Objekt, Quelle der Wahrheit.
- `locales/en.ts` – typisiert gegen die Struktur von `de` (fehlender Schlüssel = tsc-Fehler).
- `index.ts` – i18next-Init (`fallbackLng: 'de'`), typisierte Keys via `CustomTypeOptions`,
  Sprach-Ermittlung, Export `AppLanguage = 'de' | 'en'`.
- Später Namespaces/Unterobjekte pro Bereich statt einer Riesendatei.

### Sprach-Ermittlung
1. AsyncStorage-Key `app.language` (greift sofort beim Start, offline).
2. Sonst Gerätesprache via `expo-localization`.
3. Nach Login: `profiles.language`, falls gesetzt, überschreibt und wird lokal gespeichert.

### Hook `useLanguage()`
`{ language, setLanguage }`. `setLanguage`: `i18n.changeLanguage` → AsyncStorage → bei Session
Update `profiles.language`. Fehler beim Server-Update werden geloggt, lokale Wahl bleibt.

### Einstellungen
`SettingsScreen`: Abschnitt „Sprache“ mit zwei Auswahlzeilen (Deutsch / English), inline, kein Modal.

### Datenbank
Migration: `profiles.language text NULL CHECK (language IN ('de','en'))`. NULL = nicht gewählt
(Server-Default Deutsch). Bestehende Policies, kein Guard-Trigger-Eintrag. Contract-Note ergänzen
(Website nicht betroffen). `database.types.ts` ergänzen.

### Formatierung `src/utils/formatDate.ts`
Benannte Formate, Locale aus aktiver Sprache: `de` → `de-DE`, `en` → `en-GB`.
Umstellung der bestehenden Aufrufe erst in Teil 2.

### Tests
- `src/utils/formatDate.test.ts` – DE/EN-Ausgaben.
- `src/i18n/locales.test.ts` – gleiche Keys, keine leeren Strings, gleiche `{{platzhalter}}` je Key.
- Manuell iOS + Android: sofortiges Umschalten, Persistenz nach Neustart, Hermes-`Intl` mit `en-GB`.
